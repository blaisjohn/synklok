# Synklok — Setup

**Synklok** is a macOS menu bar app that auto-syncs the RME M-1620 Pro D
sample rate to its MADI input. The Windows version is covered at the end
([Windows version](#windows-version)).

## Source layout

```
Synklok/
├── project.yml                     # XcodeGen spec (regenerates Synklok.xcodeproj)
├── Synklok.xcodeproj/              # generated by xcodegen
└── Synklok/
    ├── SynklokApp.swift            # @main + MenuBarExtra
    ├── AppState.swift              # @Observable app state
    ├── Settings.swift              # UserDefaults-backed settings
    ├── LaunchAtLogin.swift         # SMAppService wrapper
    ├── Synklok.entitlements        # network.client = true, sandbox = false
    ├── Sync/
    │   ├── M1620Client.swift       # HTTP client for the device API
    │   ├── SyncEngine.swift        # poll loop + rate matching
    │   └── DeviceDiscovery.swift   # Bonjour browser
    ├── UI/
    │   ├── MenuBarView.swift       # popover content
    │   └── SettingsView.swift      # settings window
    └── Logging/
        └── Logger.swift            # ~/Library/Logs/Synklok/sync.log w/ rotation
```

## Build prerequisites

- Xcode 15+ (we developed against Xcode 26)
- Homebrew + [XcodeGen](https://github.com/yonaskolb/XcodeGen): `brew install xcodegen`

## Building

```bash
# (Re)generate the Xcode project from project.yml
xcodegen generate

# Open in Xcode and run (⌘R)
open Synklok.xcodeproj

# Or build from CLI
xcodebuild -project Synklok.xcodeproj -scheme Synklok -configuration Debug build
```

The metronome icon will appear in the menu bar. Click it for the popover.

## Distribution

Testers get a Developer ID–signed, notarized DMG: no Gatekeeper warnings,
drag to Applications, done. Requires macOS 14+.

### One-time setup

1. **Xcode → Settings → Accounts** → `+` → sign in with the Apple Developer account.
2. Create a **Developer ID Application** certificate at
   [developer.apple.com → Certificates](https://developer.apple.com/account/resources/certificates/add)
   and choose **G2 Sub-CA** (not "Previous Sub-CA", which expires 2027-02-01).
   Upload a request made in Keychain Access → Certificate Assistant → Request a
   Certificate From a Certificate Authority (Saved to disk), then double-click the
   downloaded `.cer`. Check it landed: `security find-identity -v -p codesigning`
   - Certificates last ~13 months. **Renew yearly** the same way; `release.sh`
     signs by fingerprint with whichever valid certificate expires last, so old
     and new can overlap. Delete the old one from the keychain afterwards.
   - **Never revoke** a certificate that signed a shipped build — that stops
     those copies opening. Expired is fine; Apple's timestamp keeps them valid.
3. Create an app-specific password at [account.apple.com](https://account.apple.com)
   → Sign-In and Security → App-Specific Passwords, then store it for notarization:
   ```bash
   xcrun notarytool store-credentials synklok-notary --apple-id <apple-id-email> --team-id <TEAMID>
   ```
   It prompts for the password and keeps it in the login keychain.

4. **Sparkle update key** (for automatic updates). Already created on John's Mac
   under keychain account `synklok`; its public half is `SUPublicEDKey` in
   `Synklok/Info.plist`. **Back it up** — without it, installed copies can't
   be updated:
   ```bash
   ~/Library/Caches/Synklok/spm/artifacts/sparkle/Sparkle/bin/generate_keys --account synklok -x synklok-sparkle-key.txt
   ```
   On a new Mac, import with `-f`.

### Key backup

Both keys (Developer ID `.p12` + Sparkle key, with a README) live in an
AES-256 encrypted disk image on the NAS: `znas` → `home/Backup/Synklok/Synklok-Keys-Backup.dmg`
(made 2026-10-15; password kept offline by John). After renewing the
certificate, export the new one (Keychain Access → My Certificates → File →
Export Items → .p12) and make a fresh image — never stage key files in
`~/Desktop` or `~/Documents`, which iCloud syncs.

### Each release

Bump `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` in `project.yml`, optionally
write `release-notes/<version>.html`, then:

```bash
scripts/release.sh
```

Output: `dist/Synklok-<version>-<build>.dmg` (signed, notarized, stapled), also
copied to `~/Documents/synklok-web/downloads/` with a regenerated
`appcast.xml`. **Publishing is a separate step:** commit and push synklok-web,
which deploys to synklok.app. Installed copies of Synklok check
`https://synklok.app/downloads/appcast.xml` daily and offer the update.

### First launch on a tester's Mac

- macOS asks to allow Synklok to find devices on the local network: **Allow**.
  If it was denied: System Settings → Privacy & Security → Local Network.
- Launch at login is a toggle in Synklok's settings.

## Windows version

The Windows tray app lives in `windows/` (.NET 10 WinForms; see
[windows/README.md](windows/README.md)). It builds and ships entirely from the
Mac. It shares the Mac's version number (`project.yml`) and Sparkle update
key; everything else is separate.

| Piece | Where |
|---|---|
| Installer | `Synklok-<version>-<build>-Setup.exe`, NSIS, per-user (no admin): `%LOCALAPPDATA%\Programs\Synklok` |
| Download | GitHub release `windows-<version>` on blaisjohn/synklok (Cloudflare Pages caps files at 25 MB; the installer is ~34 MB) |
| Stable link | `synklok.app/download-windows` → that release asset (`_redirects`) |
| Update feed | `synklok.app/downloads/appcast-windows.xml`, read by [WinSparkle](https://winsparkle.org) daily |
| Signing | **Not code-signed for now** (John's call, Oct 2026), so Windows shows its SmartScreen warning on first install. Updates are verified with the Sparkle EdDSA key either way. Optional Authenticode signing via Azure Artifact Signing: see below |

### One-time setup (Windows)

1. .NET 10 SDK in `~/.dotnet` (not on PATH; the scripts add it).
2. `brew install makensis`

### Optional: code signing (not set up)

In October 2026 John decided not to pay for signing yet. A newly signed
publisher still gets SmartScreen's "Windows protected your PC" until it has
hundreds of installs, so for a small audience $9.99/month mostly changes the
publisher line from "Unknown" to "John Blais". Reasons to switch it on later:
someone's PC blocks it outright (Windows 11 **Smart App Control** refuses
unsigned apps with no "Run anyway"), more users, or a studio that requires
signed software. Free alternatives to look at first: SignPath Foundation
(open-source projects, builds on GitHub Actions) or the Microsoft Store.

Already done: an Azure pay-as-you-go account on John's personal Microsoft
account (john.blais@gmail.com, billing account type Individual) with
`Microsoft.CodeSigning` registered. No signing account exists, so it costs
nothing. To switch signing on:

1. `brew install jsign azure-cli osslsigncode`, then `az login` (browser).
2. Create the Artifact Signing account (billing starts, $9.99/month Basic):
   `az group create -n synklok -l eastus` and
   `az artifact-signing create -n synklok -l eastus -g synklok --sku Basic`
   (the extension: `az extension add --name artifact-signing`).
3. On the account in portal.azure.com: Access control (IAM) → give yourself
   **Artifact Signing Identity Verifier** and **Artifact Signing Certificate
   Profile Signer**.
4. Identity validations → Individual → New identity → Public; finish the
   AU10TIX ID + selfie check on the phone (Microsoft Authenticator). The name
   and address come from the Azure billing account and must match the ID.
5. Certificate profiles → Create → Public Trust, linked to that validation.
6. Put the account and profile names at the top of `scripts/sign-windows.sh`
   and check with `scripts/sign-windows.sh --check`. From then on
   `release-windows.sh` signs every file automatically.

Microsoft issues a new 3-day certificate behind the scenes for every signing
session; jsign timestamps each signature, so shipped installers stay valid
after that and even if the Azure account is later cancelled.

### Each release (Windows)

1. Bump `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` in `project.yml` (shared
   with the Mac; ship whichever platforms changed, a platform may skip a number).
2. Optional notes: `release-notes/<version>-windows.html` (shown in the update window).
3. `scripts/release-windows.sh` — tests, builds (and signs, if set up), writes the installer to
   `dist/windows/`, adds it to `synklok-web/downloads/appcast-windows.xml` and
   points `/download-windows` at its GitHub URL. Nothing is public yet.
4. Commit and push this repo.
5. `scripts/release-windows.sh --publish` — creates the `windows-<version>`
   GitHub release and uploads the installer (public).
6. Commit and push synklok-web — publishes the feed and the download link.

The script builds the last commit (a `git archive` of HEAD), so uncommitted
work in this shared working tree never ships. Commit first.

Testing:
- **Update test on a PC, nothing public:** after step 3, run
  `scripts/test-windows-update.sh`. It serves the new installer and a copy of
  the feed from this Mac on port 8091, and builds an older "localtest" installer
  that reads it. Install that on the PC, then Check for updates….
- **Shareable test build:** `scripts/release-windows.sh --test-build 3`
  (→ `dist/windows/test/`, reports itself as `<version>-test3`, build 3) and,
  once the code is pushed, `scripts/release-windows.sh --publish-test 3` makes a
  GitHub *pre-release* `windows-<version>-test3`. It reads the real feed, so it
  updates itself to the finished release once that's published.

The Mac's `scripts/release.sh` and `release-windows.sh` each rewrite only their
own line of `synklok-web/_redirects`.
